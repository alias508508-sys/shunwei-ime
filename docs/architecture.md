# 实现架构与设计取舍

2026-10-09，首个规则与词典原型。

## 当前路径

`编辑事件 → session/revision → 保护片段 → 拼音/英文/缩写联合词图 → 有限宽度搜索 → 词频/词性排序 → 候选 → 用户确认 → 提交/受控撤销`

TypeScript 核心为 Vite 网页调用；同一份代码由 esbuild 打包为 IIFE，由 Swift 通过系统 JavaScriptCore 执行。这样网页与 Mac 直接共享解码实现，避免一开始重复维护两种算法。主线程上的原型解码是同步的，session 模块已提供异步结果一致性检查接口；神经模型重排尚未实现。若长串或模型推理性能不满足要求，再抽取后台工作线程，不能将当前同步实现宣称为非阻塞 AI 推理。

中文来源为 CC-CEDICT 的词与拼音，结合 jieba 词频/词性。英文成员词来源为 cmudict，另用项目整理的功能词和技术缩写增强排序。分段不是贪心最长匹配：保留多条路径，并保留全中文候选、混输候选与原文。beam 总宽度32，每类路径最多16；中文词图的相同拼写不同音节切分分别保留候选。

频次、词性组合与上下文的得分都是启发式排序值，不是概率，也不是神经 AI。输入超过256个 UTF-16 单位时先整体保留原文，尚未实现长文本逐段修复。读音的声调归一化可识别，但不据此限制同音不同调候选，数字声调与教学评分待下一阶段。

## librime 评估

检查本次保存的 `data/upstream/rime_api.h`：`get_context` 返回组合区、候选菜单和预览，另有候选枚举与选择 API。组合信息含 preedit、光标与选区；该接口不直接提供本项目所需的每个中英联合片段来源区间。因此无论使用 librime 还是自有词图，上层都需要联合分段与保护片段逻辑。

本机没有已安装的 librime。本轮采用可在网页和 JavaScriptCore 中运行的词图解码；没有为了技术试验额外安装全局 Homebrew 库。librime 运行集成和与当前排序的对比留待下一阶段，当前没有声称使用 librime 产生候选。

## Mac 层

- `SmartInputController`：真实 InputMethodKit 入口，转发系统事件。
- `CompositionCoordinator`：每个控制器独立实例，组合缓冲、光标、候选、菜单和受限恢复。
- `CandidatePanel`：非激活窗口显示候选，缺少有效坐标时隐藏；多个屏幕按插入点定位。
- `Engine`：应用内共享不可变词图，通过 JavaScriptCore 解码；不跨客户端保存上下文。
- `Preferences`：本机用户主动添加的词条，存于 `~/Library/Application Support/Shunwrite/entries.json`。

Mac 当前按一次空格确认，Return 原文提交，Esc 取消组合。标点作为组合区原文保留，下一次确认时一起提交，以避免输入 URL 时冒号或点触发提前转换。失焦/停用按原文结束组合，优先保存输入。只恢复焦点及提交范围仍可验证的一次提交；读取不到范围或选区变化时拒绝修改。

## 验证边界

InputMethodKit 入口依赖系统的客户端代理。直接将普通 mock 当作 IMK 客户端构造控制器会被框架拒绝，实测抛出 `unexpected client proxy`。因此把可测试组合行为抽为协调器，用实现 IMKTextInput 的受控客户端测试，保留真实入口转发。这个测试证明协调器的编辑行为，不证明 TextEdit、浏览器、Word 等宿主兼容性。

还需用户在系统设置启用后完成真实宿主输入测试；系统注册/启用、候选窗鼠标交互、菜单、办公软件行为不能以协议客户端测试替代。

## 下一阶段

3. 在此基线与真实宿主稳定后，评估本地 AI 候选重排或 librime 解码，记录增益与耗时。
4. 教师审核拼音规范与题库后单独开展学习模式。
